# D-1006-LEGACY-NOSTR-01 — existing Nostr store migration

## Decision and user outcome

Issue #1006 is not complete if an existing Nostr gateway database cannot be opened after upgrade without losing the user's identity, signing key, settings, watches or allowed senders. The accepted old gateway store has schema-0 `instances(agent_id, agent_name, secret_key, relays_json, filter_json, enabled, owner_pubkey, self_pubkey, updated_at)`, plus `watches`, `allow_identities` and `gateway_meta`. The current S8 importer handles a v56 core and current S5 destination, not this existing source. A QC-only conversion or a freshly initialized store does not solve this defect.

## Minimal production change

1. Extend the existing stopped `opencrab-gateway-migrate` S8 phase, not daemon startup or a third core writer. Detect the exact legacy Nostr store schema **before** `NostrStore::open` runs `CREATE TABLE IF NOT EXISTS`; an unknown or mixed schema refuses without mutation. Core's ordinary numbered migrations may bring a stopped copy to v56; they do not change the original old gateway store.
2. Read every old `instances`, `watches`, `allow_identities` and `gateway_meta` row. For each old `agent_id`, require one and only one existing, undeleted core Nostr instance and matching subject/agent/binding. Reuse its `instance_id` and subject, never derive or allocate a replacement. The historical gateway import copied core settings **once**, then `upsert`, `set_enabled` and `set_self_pubkey` updated only the gateway store. Consequently the old gateway is authoritative for its mutable name, relays, filter, enabled flag, self key, signing key, watches and allowed identities; the old core may legitimately be stale. Compare parsed/normalized semantics, not raw JSON formatting. Merge only these gateway-owned fields into the existing core Nostr config, retaining core-only fields and every existing ID, binding and session. Require each old watch's session to resolve to its existing bound session; where a corresponding core watch is present its session/filter/interval must agree or the gateway-owned watch must be explicitly reconciled into the existing S8 heartbeat projection. Old `allow_identities` is the active admission authority. A stale core `trusted_users` Nostr row absent from that set is still covered by a fingerprint-bound approved disposition, but goes only into the existing Nostr `legacy_identity_sources` **inert** history table, never active `identity_projections`; an old gateway identity present in both sources produces exactly one active projection with the gateway role. No source row is dropped, and a removed sender is never re-admitted by migration. Preserve each old row in the destination or refuse if it cannot be represented; no silent drop or invented authority.
3. Credential authority is the old gateway's `secret_key` **after decoding**: the historical store may already hold an `enc:v1:` envelope, while earlier rows may contain plaintext. Detect the exact historical format, decrypt encrypted rows with the historical owner-only master key using its existing implementation, refuse missing keys/decryption failure, and compare the resulting signing-key bytes against any independently present core or S5 candidate. Unequal candidates refuse. Encrypt those plaintext signing-key bytes into the S5 envelope with the existing S5 store path and owner-only master key; never double-encrypt an old envelope, print or persist plaintext in a manifest, or accept an empty key for an enabled instance.
4. Retain current user-visible admission, watch/filter/relay configuration and lifecycle intent. Map old allowed identities to gateway-owned projections and watches to the already defined gateway config/generic heartbeat target where their exact semantics match; preserve historical source rows if needed for lossless retention. If an old field cannot be represented without changing behavior, refuse rather than silently ignore it. Do not add a live old-schema fallback to the daemon.
5. Prevalidate source and destinations, make one SQLite-consistent matched backup set including the old gateway DB **before any conversion write**, then convert that destination atomically as part of S8 import. The same existing `project-core-state` transaction may reconcile **only** a semantically changed legacy-Nostr instance's generic core config/digest/enabled/revision, using the existing `revise_gate_instance` revision semantics (one increment, stale operation declaration cleared); the destination records that resulting revision/digest. No core instance/binding/session/subject ID is rewritten, and unrelated kinds or identical configurations remain unchanged. Approval and verification bind the old-store source fingerprints and this revision change. A failed core projection requires operator whole-set restore; a completed rerun must not increment again. This is a narrow exception to S8's previous ban on modifying `gate_instances`, necessary to preserve ordinary historical gateway-only edits. Never run the candidate against the sole live DB or alter the accepted QC source asset.

## Proof and scope

- Assertion-level RED uses the actual old-store schema (instance plus watch/allowed identity) at the production `gateway-migrate` entry: current importer rejects or leaves it unusable; no helper-only proof. Further REDs represent legitimate gateway-only changes after the historical initial import: changed settings must reconcile core config/digest/revision without changing IDs or bindings, and a sender removed only from old gateway admission must remain inert even when the old core retains that sender. GREEN reopens the migrated store through current `NostrStore`, preserves stable core IDs and all semantically relevant old rows/credential equality, then starts the existing くらぶ identity on an isolated **copy** for one ingress→reply QC case.
- Include a refusal case for an ambiguous/missing core association or conflicting credential; keep the existing schema-56/current-S5 behavior unchanged. Verification reports contain counts/digests only, no identifiers or secret material. Do not broaden into generic migration framework, unrelated hardening, delivery changes, new authentication, README changes, or real-data cleanup.
- The existing original QC and production databases remain untouched until the conversion and isolated QC pass. Real cutover/cleanup stays separately gated by a stopped matched backup and explicit scope.

This design supersedes S8's assumption that all Nostr destinations are already S5, only for an actually present legacy Nostr store. It does not assert that Discord/Web have the same old schema; their existing paths remain unchanged unless a separately observed live source proves otherwise.
