# ゲートウェイ仕様概要――利用者から見えること

この文書は、opencrab で自分のエージェントを運用する人のための仕様概要です。
設定ファイルや内部構造の説明ではなく、「どこから何が入り、いつエージェントが反応し、外へ何ができるか」をまとめます。
ここに書くのは目標仕様です。設計済みであっても、まだ実装・提供されていない範囲はその旨を明記します。

実装上の詳細は、[Discord gate 設計](./discord-gate.md)と[Nostr gate 設計](./nostr-gate.md)を参照してください。

## ゲートウェイとは何か

ゲートウェイは、エージェントの中核である core と、Discord、Nostr、Web など外の場をつなぐ配送係です。
外から届いた投稿や操作を core へ運び、core が作った返事や操作を外のサービスへ届けます。
役割分担は「判断は core、配送はゲートウェイ」です。

ゲートウェイが判断しないことには、たとえば次があります。

- 誰の発言をエージェントに考えさせるか
- すぐ反応するか、複数件をまとめるか
- 返事をする権限があるか
- 返事をせず終了するか
- どの会話や作業の続きとして扱うか

ゲートウェイが担当することには、たとえば次があります。

- 外部サービスへの接続
- 届いたデータの形式や署名の確認
- 設定された購読条件への機械的な照合
- core への入力の配送
- core が許可した投稿、リアクション、操作の実行

この分担により、サービスごとに配送方法が違っても、エージェントの人格、権限、会話判断は core 側で一貫させられます。

## 共通の考え方

### 種類とインスタンス

「種類（kind）」は、Discord、Nostr、Web のような接続方式の違いです。
「インスタンス」は、その種類を実際に利用する一つの接続主体です。

- Discord では、bot アカウント一つが一つのインスタンスです。
- Nostr では、エージェント用の鍵一つが一つのインスタンスです。
- 一つのインスタンスは、一つの独立したプロセスとして動きます。

同じ種類のインスタンスを複数、同時に動かせます。そのため、複数の bot や複数の Nostr アカウントを一つに混ぜずに運用できます。
設定、認証情報、稼働状態もインスタンスごとに分かれます。一つが停止しても、それだけを失敗として扱い、ほかの接続まで止めません。

### 場

「場」は、エージェントが会話や出来事を受け取る単位です。
Discord のチャンネルが、場を理解するための基準です。同じ場所で続く投稿は、同じ場の出来事として扱われます。
Nostr では、watch で選んだタイムライン全体が一つの場になります。relay 一つごと、投稿者一人ごとに場が分かれるわけではありません。

場には、誰が参加できるか、入力してよいか、出力してよいか、定期的に動かすか、といった運用上の判断が結び付きます。

### 権限

core は、入力した人を次の三つの権限層として扱えます。

- オーナー: エージェントの運用者として確認された相手
- 信頼: フォロー関係や明示的な許可などで信頼された相手
- 不明: 上のどちらにも確認できない相手

表示名が似ている、別の接続で同じ人に見える、といった推測では権限を補いません。確認できない場合は、広く許可する側ではなく、不明として安全側に倒します。
入力を受け取った時点の権限を記録するため、あとで信頼関係を変更しても、過去の入力の扱いは遡って変わりません。

### 即応とまとめ入力

外からの入力には、すぐ処理する「即応」と、一定時間の出来事をまとめる「まとめ入力」の二つの考え方があります。
まとめ入力では、オーナー、信頼、不明の層ごとに別の待ち時間を持てます。ある層の最初の入力から時間を数え、期限までの同じ層の入力を一回にまとめます。
新しい入力が来るたびに期限が延び続けることはありません。異なる権限層の入力も、同じ一回へ混ぜません。
即応する入力が来た場合は、同じ層ですでに待っていた入力も一緒に処理し、あとから同じ内容をもう一度処理しないようにします。
この二層入力を明示的に使うのが、後述する Nostr のタイムラインです。どの入力を即応にするかは配送係ではなく core が決めます。

### 配送時の安全側の振る舞い

送信先、権限、接続先を一意に決められない場合、推測して別経路へ送りません。
外部サービスが操作を受け取ったか不明な場合も、重複投稿を避けるため、自動的に同じ操作を繰り返しません。

## Discord でできること

### 反応する契機

Discord から core へ入る契機は、次の二系統です。

- 新しいメッセージ
- エージェントが出したボタン、選択欄、フォームへの操作

メッセージ本文と画像添付を入力として扱えます。画像以外の添付は、添付があることを示す注記として扱います。
自分自身の bot が送ったメッセージは入力へ戻しません。ほかの bot のメッセージは、それだけを理由に除外しません。
ただし、見えたメッセージがすべてエージェントへ届くわけではありません。

- サーバー内では、利用を許可したチャンネルだけが対象です。
- DM では、オーナーまたは信頼済みの相手だけが対象です。
- スレッドは、現在の対象外です。

許可されていない場所は、会話履歴や参加状態を作らずに無視します。

### 返答と操作

エージェントは、許可された場で次の出力を行えます。

- メッセージを送る
- リアクションを付ける
- ボタン、選択欄、フォームを含む対話 UI を送る
- 応答を考えている間、入力中であることを表示する

利用できる Discord 操作は、次の六つです。

- 参加しているサーバーの一覧を見る
- サーバー内のチャンネル一覧を見る
- チャンネルを作る
- webhook を作る
- 指定メッセージへリアクションを付ける
- ファイルを送る

core 側の機能として、次も利用できます。

- チャンネルごとの利用方針を設定する
- 通常用途または下位タスク用の webhook を用意する
- 別のエージェントへレビューを依頼する
- 対話 UI を送る

チャンネルの方針は、bot がまだそのチャンネルを観測していなくても設定できます。ただし、設定しただけで会話の取り込みが自動的に始まるわけではありません。

### 複数 bot を同じ場所で使う場合

同じチャンネルに複数の bot インスタンスを置けます。
同じ外部メッセージを複数の bot が観測しても、一つの出来事として重複を取り除きます。
その場への参加を許可された各エージェントには、一回ずつ入力されます。どの bot が先にメッセージを観測したかで、発火回数は変わりません。
送信時には、エージェント専用の bot がその場で使える場合はそれを選び、なければ、そのエージェントを含む共有 bot を選びます。
一度選んだ bot が送信時に利用不能でも、別の bot へ自動で切り替えません。意図しないアカウントから発言することを防ぐためです。

### Discord でまだ無いもの

現在の設計範囲は非 voice 機能です。

- voice チャンネルへの参加と退出
- 音声の受信
- 音声認識と音声合成

これらは後続の voice 対応で追加する予定で、現時点では利用できません。また、次も現在の入力範囲には含まれません。

- メッセージの編集や削除を出来事として受け取ること
- リアクションの追加や削除を出来事として受け取ること
- スレッドでの会話取り込み
- 過去履歴の自動取り込み
- 送信失敗時の自動再試行や、別 bot への自動切り替え

## Nostr でできること

Nostr のこの仕様は実装前の目標設計です。設計への合意は、現在の実装ですべて利用できることを意味しません。

### watch でタイムラインを場にする

利用者は watch を設定し、エージェントが見るタイムラインを決めます。

watch では、次の観点を組み合わせられます。

- 自分宛てのメンション
- 指定した投稿者
- 本文に含まれる指定キーワード
- 対象とする Nostr の event 種類

メンション、投稿者、キーワードは、いずれかに合えば候補になります。そのうえで、指定した event 種類に含まれるものだけを受け取ります。
キーワードは大文字と小文字を区別する単純な部分一致です。暗号化 DM は、この watch の対象ではありません。
watch で選ばれたタイムラインが一つの場です。watch や relay の設定を変更しても、場そのものを別の場に作り替えません。

### 即応する入力

オーナーまたは現在のフォロイーから届いた次の入力には即応します。

- エージェント自身へのメンション
- エージェント自身の投稿へのリプライ
- エージェント自身の投稿へのリアクション

三条件のどれかだけでは即応になりません。相手がオーナーまたはフォロイーであり、かつ自分宛てであることが必要です。
オーナーやフォロイーの通常投稿、プロフィール更新、ブースト、他人宛てのリプライやリアクションは即応せず、まとめ入力へ入ります。
信頼済みでもフォロイーではない相手は、同じ形の入力でも即応しません。

### まとめて入力するもの

即応条件に当てはまらない watch 内の入力は、指定した間隔でまとめます。
待ち時間は、オーナー、信頼、不明の三層それぞれに設定します。三つとも正の時間を明示する必要があり、未設定の既定値はありません。
接続直後に届く過去の投稿も、通常の投稿と同じ時間窓へ入ります。初回だから即時処理する、件数が多いから早く処理する、という特例はありません。
同じ投稿が再接続時に再び届いても、すでに処理したものは重複入力しません。

### 複数 relay

一つの Nostr インスタンスに複数の relay を設定できます。すべての relay へ同じ watch を張り、各 relay は独立して再接続します。
同じ event が複数の relay から届いても、一つの入力として扱います。一つの relay が停止しても、少なくとも一つで購読できていれば動作を続けます。
投稿時は一度だけ署名し、同一の event を設定済み relay へ送ります。少なくとも一つが受理すれば送信成功です。
すべてが拒否した場合は失敗です。受理を確認できず結果が不明な場合は、重複を避けるため自動再送しません。

### 扱える Nostr の出来事と出力

watch では、通常投稿、プロフィール、ブースト、リアクションを区別して扱えます。そのほかの指定済み event 種類も、元の種類と内容を保ったまま入力できます。
エージェントは Nostr へ投稿でき、プロフィール更新も実行できます。誰がプロフィールを変更してよいかは、ゲートウェイではなく core が判断します。

### Nostr でまだ無いもの、行わないもの

- この目標仕様そのものは、まだ実装前です。
- 暗号化 DM の購読は対象外です。
- 権限層ごとの待ち時間には既定値がなく、運用者による指定が必要です。
- relay ごとに別の場を作ることはしません。
- 接続完了通知や初回履歴を理由に、まとめ入力を早めることはしません。
- 結果不明の投稿を、自動で再署名・再送することはしません。
- オーナーやフォロイーを確認できない時に、表示名などから推測して許可しません。

## 利用者が設定するもの

設定ファイルの書式ではなく、運用時に決める概念を一覧にします。

### すべてのゲートウェイに共通

- 利用するゲートウェイの種類
- 動かすインスタンスと、それを所有するエージェント
- 各インスタンスを有効にするか、停止しておくか
- 外部サービスへ接続するための認証情報
- どの場をどのエージェントに入力してよいか
- どの場へ出力してよいか
- 利用を許可する操作
- 定期実行や heartbeat を使うか

### Discord

- bot アカウントと token
- 専用 bot と共有 bot のどちらとして使うか
- 共有 bot を利用できるエージェント
- オーナーとして扱う外部アカウント
- サーバー内で利用を許可するチャンネル
- DM を許可するオーナー／信頼済みユーザー
- チャンネルの読み取り、書き込み、定期動作の方針
- 各エージェントから見せる Discord 操作

### Nostr

- エージェント用の公開鍵と秘密鍵
- オーナーとして扱う公開鍵
- 接続する一つ以上の relay
- watch の投稿者、キーワード、event 種類
- 自分宛てメンションを含む watch
- オーナー、信頼、不明の各層のまとめ間隔
- 利用を許可する投稿やプロフィール操作

## 仕様レビューへのお願い

利用者として「この場面でどう動くのか分からない」「必要な設定が足りない」「できるように読めるが実際は未対応ではないか」と感じた点があれば、仕様への質問や不足の指摘を歓迎します。
